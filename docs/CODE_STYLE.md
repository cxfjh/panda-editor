# 编码规范

改代码、加功能之前先看这份。三条底线：

1. 一个文件只干一件事
2. 一层只依赖下一层，不许回头依赖
3. 对外只暴露一个入口，内部实现随便改都不该影响调用方

**适用范围**：本文管结构与组织，包括分层、拆文件、依赖方向、新增功能的落点。自动生成的代码不受约束，包括编译器产物、代码生成器输出、脚手架模板，这些文件不要手改，改生成器。

目录名和类名可以各不相同，下文用「界面层」「业务层」这类角色名指代，落到具体项目时对应到自己的目录即可，只要全项目统一。

---

## 一、目录与职责

按角色分层，每层只做一类事：

| 层         | 放什么                                         | 不该放什么                 |
|------------|------------------------------------------------|----------------------------|
| 入口       | 装配：读配置、初始化日志、启动主流程           | 任何业务逻辑               |
| 界面层     | 把状态画到屏幕上，接收用户操作                 | 与展示无关的计算           |
| 可复用部件 | 独立可复用的控件或组件，不含整页编排           | 只给某一个页面用的临时代码 |
| 业务层     | 规则、流程、领域逻辑，不碰界面                 | 弹窗、控件、布局           |
| 数据层     | 数据结构、映射表、静态数据                     | 带分支的流程               |
| 工具层     | 无业务倾向的通用函数：时间、字符串、文件、编码 | 业务规则、界面             |
| 脚本目录   | 生成器、打包、迁移脚本                         | 运行时会被 import 的代码   |

依赖方向是单向的：

```
入口  ->  界面层  ->  业务层  ->  数据层 / 工具层
```

工具层是最底层，它不能依赖界面层和业务层。反向依赖一律不允许。

判断方法：底层模块如果 import 了上层的 **运行时**对象，就是错的；只引入类型声明、且在类型检查块内的，允许。

两处需要拆走的情况：

- 上层导出了一个纯函数给下层用，说明这个函数放错了层，把它移到下层
- 下层需要上层的数据才能工作，改成由上层通过参数传进来

## 二、文件规模

| 行数       | 结论                                   |
|------------|----------------------------------------|
| 200 以内   | 理想区间                               |
| 201 到 400 | 可接受，前提是只有一个职责             |
| 400 以上   | 必须拆，例外只有两类，且要在评审时说明 |

两类例外：

- 纯数据表，比如一张几百行的映射规则列表，没有分支逻辑
- 单一职责且对外只有一个入口的模块，比如只做配置读写的模块

拆不拆看职责，不看行数。一个 700 行的终端组件同时管进程、命令、历史、报错、样式五件事，就该拆；一个 400 行的配置模块只做一件事，可以留着。

出现下面任意一条就该动手：

- 文件里能数出两个互不相干的职责
- 改一个功能要同时动这个文件里五处不相关的地方
- 顶部 import 超过 20 个，跨了三个以上领域
- 想给某个私有方法加 `# 以下属于 XXX 部分` 这种分隔注释

拆分成包的四步：

1. 给现有方法按业务域分组，写出每组一句话职责
2. 建同名目录，每组一个模块，文件名用职责命名
3. 对外主类单独一个文件，其余用 mixin 或独立函数
4. 包入口只做转出，保证外部 `from 原模块 import 原名字` 一行都不用改

第 4 步是硬要求。拆分不能要求调用方跟着改，否则一次重构会波及全项目，回归范围失控。

## 三、包内怎么组织

```
包名/
├── __init__.py     只导出对外符号，不写逻辑
├── refs.py         共享成员声明，仅当包内多个 mixin 互相引用时才建
├── widget.py       对外主类
├── constants.py    常量与命令表
├── styles.py       样式表
└── xxx_actions.py  按业务域拆的动作
```

命名按角色，不按顺序。常见文件名的含义固定：

| 文件名                             | 含义                              |
|------------------------------------|-----------------------------------|
| `widget.py` `manager.py` `view.py` | 对外主类                          |
| `refs.py`                          | 共享成员的类型声明，只标注不赋值  |
| `constants.py`                     | 常量表、命令表                    |
| `styles.py`                        | 样式表、配色                      |
| `loader.py`                        | 后台线程                          |
| `operations.py`                    | 数据或文件的增删改                |
| `xxx_actions.py`                   | 某一类用户动作，如 `file_actions` |

包入口的两条规矩：

- 只允许出现 import 和 `__all__`，一旦出现 `if`、函数或常量计算，就已经错了
- 新增对外符号时同步补进 `__all__`，否则自动补全和静态检查都看不到

## 四、共享状态怎么声明

包内多个 mixin 都要访问的属性，集中放在 `refs.py` 的声明类里：

```python
class EditorRefs:
    """编辑器共享成员的声明"""
    _text: TextEdit
    _dirty: bool
```

三条禁令：

1. 禁止用 `self.xxx = None` 当声明。它是第二处初始化，谁先执行全看有没有调 `super().__init__()`，迟早覆盖掉真实值
2. 禁止写空方法体 `def foo(self): pass` 占位。声明类在方法解析顺序里一旦靠前，就会把真实现挡住，而且不报错
3. 声明类必须留在继承列表里，且不要在它上面定义任何会覆盖的方法

## 五、新增功能的固定路径

同一件事通常在三个地方各登记一次：定义、注册、展示文案。只改一处是这类改动最常见的错误来源。

| 要加的东西 | 改哪里                                   | 容易漏的点                                                 |
|------------|------------------------------------------|------------------------------------------------------------|
| 数据表条目 | 表定义处，以及读取这张表的注册处         | 两处名字必须完全一致，否则查表查不到；有生成产物要重新生成 |
| 界面动作   | 动作定义、挂到菜单或工具栏、文案与快捷键 | 漏文案会显示成内部标识符；信号连接漏了点了没反应           |
| 配置项     | 默认值、读取处、界面上的勾选回填         | 只在读取处加默认值，重启后界面状态会错                     |
| 工具函数   | 归到同类模块里                           | 不要为一个函数新建文件                                     |
| 界面部件   | 部件目录，按第三节模板                   | 部件不直接读配置，由调用方传入                             |
| 第三方依赖 | 依赖清单文件                             | 写清版本范围，别只写包名                                   |

数据表驱动的部分要守住一条：加内容改表，不要改生成逻辑。生成器里出现为某一条数据单独写的 `if`，说明表结构缺字段，回头补表。

## 六、统一入口

同一类操作只允许一个入口，禁止各处自己实现一份。

| 要做的事       | 用什么                 | 不要用什么                    |
|----------------|------------------------|-------------------------------|
| 读写配置       | 统一的配置对象         | 到处 open 配置文件            |
| 记日志         | 统一的日志接口，带级别 | `print`，或各处自定义 handler |
| 提示用户       | 统一的提示封装         | 随手弹原始对话框              |
| 跨线程通知界面 | 框架提供的信号机制     | 子线程里直接改控件            |
| 读写文本       | 统一的编码封装         | 每处自己猜编码                |
| 取当前时间     | 统一时钟来源           | 到处写 `datetime.now()`       |

日志的取舍：应用层失败要记，包括配置、文件读写、编译、线程、外部库解析；用户输入导致的错误不记，那些已经有提示。

---

## 七、禁止事项

1. 一个文件里塞第二个职责
2. 互相 import 成环，需要双向调用时把公共部分抽到下层
3. 包入口里写逻辑
4. 手改生成产物
5. 硬编码绝对路径，路径从配置或当前文件位置推
6. 用 `print` 代替日志
7. 留 `except: pass` 不记日志
8. 留未使用的 import 和调不到的死函数
9. 新增依赖不写进依赖清单
10. 提交调试代码、注释掉的旧实现

## 八、注释规范

### 文件顶部注释规则

1. 禁止在文件顶部写 `#` 注释；模块说明写到模块 docstring 里
2. `#` 注释不得出现在任何 import 之前，否则会破坏部分文件级别的编译指令

### 导入语句规则

1. 禁止使用括号换行
2. 允许单行逗号分隔：`from xxx import a, b, c`
3. 所有导入必须单行完成，不允许任何形式的换行

### docstring 规则

1. 内容限制
    - docstring 只允许包含 摘要、Args、Returns、Raises 这四类区块，禁止示例、备注、版本等其它自定义内容
2. 强制规则
    - 函数、类必须编写 docstring
    - 函数存在Args 或者 Returns 时，Args区块、Returns区块必须书写，不可省略
    - 类固定使用单行 docstring 格式 `"""摘要内容"""`，不使用多行区块
3. 排版规则
    - 函数多行格式：`"""` 单独占一行
    - 摘要单独一行，摘要为单行文本，不可换行拆分；摘要末尾不加结束符号
    - 摘要和第一个区块之间保留一个空行
    - 区块顺序固定：摘要 → Args → Returns → Raises
    - 固定标签：Args: / Returns: / Raises:，标签末尾半角冒号必须保留，标签垂直对齐
    - Args、Returns、Raises的说明统一缩进 4 个空格，和标签对齐
    - 不存在的区块直接省略，不要保留空区块
    - 类统一单行格式：`"""摘要内容"""`
    - 函数只要有Args或Returns或Raises，强制多行 docstring，不能使用单行写法
4. 字符与格式限制
    - 所有标点全部使用半角
    - 禁止使用任何括号，包括中文括号、英文括号
    - 禁止书写序号、==== 或者 ---- 这类分割装饰线
    - 注释内出现英文单词、标识符，英文左右两侧增加空格
5. 其它约定
    - 函数签名已有类型注解，docstring 不再重复标注类型
    - 禁止多余空行、装饰符号、尾随空格

### 单行注释规则

1. 表达要求
    - 注释文字精准表达意图，不写冗余、模糊描述
    - 关键逻辑代码必须补充注释
2. 层数限制
    - 单行 `#` 注释不能叠加两层，禁止连续两行及以上全部是 `#` 注释；多段说明改用函数 docstring
3. 空行规则
    - 如果单行注释上方存在代码行，注释与上方代码之间必须空一行（注释位于代码块起始位置，上方无代码时，不需要空行）
    - 注释紧贴下方对应的代码，注释和下方代码之间不需要空行
    - 注释在代码块最开头，上方没有代码，不需要空行
4. 字符与格式限制
    - 禁止使用任何括号，包括中文括号、英文括号
    - 禁止书写序号、==== 或者 ---- 这类分割装饰线
    - 注释内出现英文单词、标识符，英文左右两侧增加空格
5. 位置特例
    - 代码行尾注释，即同行注释，不受上面空行约束，项目尽量少用行尾注释

## 九、提交前自查

- [ ] 改动涉及的文件都在 400 行以内，超了有明确理由
- [ ] 没有新增反向依赖，底层没有 import 上层的运行时对象
- [ ] 拆包时外部 import 路径不用改，包入口导出补全
- [ ] 生成产物已重新生成，和源码一起提交
- [ ] 三处登记都改了：定义、注册、展示文案
- [ ] 注释符合第八节
- [ ] 没有 `print`、裸 `except`、未使用导入、调试残留
- [ ] 新增依赖已写进依赖清单
- [ ] 实际跑过一次，不是只看能不能编译

验证要求按项目类型区分：

- 命令行项目：跑一遍主流程，确认输出与退出码正常
- 界面项目：至少启动一次，且实际操作一遍改动涉及的入口
- 涉及后台任务：确认失败路径有日志，正常路径不刷屏

改动越靠近底层，验证范围要越大。只改了工具函数也要把调用它的主流程跑一遍。
